# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository content

- `docs/index.html` — the entire site: **one short scrolling page** covering all of 2024 (~44.2M cleaned trips). It was deliberately cut to ~1,300 words; keep it that way: one-sentence section intros, no narrative report, no secondary charts. Sections in order: hero with three key findings, demand (`#demand`: hour-by-day heatmap, daily rides, temperature bars, rain/holiday effects), where (`#where`: Leaflet ridership map + a borough table), rebalancing (`#rebalance`: net-flow map + top-5 tables), forecast (`#forecast`: accuracy by planning level, example week with 80% band, method table, backtest, dispatcher and band tables), and a compact method list (`#method`). The interactive pieces are separate blocks in one inline `<script>`, each wrapped in `runSection(name, function () { ... })` (catches and logs errors so one failing section can't stop the others) with its own DOM ids. A `runSection` body throws if an element it fills is missing, so remove the JS when you remove the HTML.
  - **Prose numbers are bound to the data.** The hero, section headings and method list are hand-written, but every number in them is wrapped as `<span data-fact="name">…</span>` (README uses `<!--fact:name-->…<!--/fact-->`). `scripts/sync_facts.py` defines each fact from `docs/data/*.json`; `--write` refreshes them all after a rebuild, and CI runs `--check`, failing on any stale number. When you add a number to the prose, add a fact for it rather than typing it bare. Wording that depends on a result's *direction* (e.g. "no better than the 7-day rule") is not checked automatically; reread it after a rebuild.
  - `docs/assets/charts.js` — small dependency-free SVG chart helpers (`Charts.lineChart`, `scatterChart`, `barChart`) used by the seasonality, rebalancing and forecast sections: one y-axis, nice ticks, crosshair/per-bar tooltips (filled with `textContent`, never `innerHTML`, since station names are data), redraw on resize and on light/dark change. Series colors are `{light, dark}` pairs validated per mode with the dataviz skill's `validate_palette.js`: blue `#2a78d6`/`#3987e5`, orange `#eb6834`/`#d2611f` (the light orange fails the dark-mode lightness band, hence the darker step), red `#e34948`/`#e66767`. Rebalancing uses a diverging red (loses bikes) ↔ gray ↔ blue (gains bikes) scale.
  - Staten Island has zero Citi Bike stations (verified, not a bug). `summary.json`'s `by_borough` is pre-seeded with all 5 boroughs so the borough table always has a row for it. (The page used to have five per-borough mini-maps; they were removed for length and are in git history before November 2026.)
  - Wording: weather effects are associations ("days with rain at commute hours have X% fewer rides"), not causal claims ("rain cuts rides").
  - Design tokens, nav, and card/stat-tile/footer styles live in `docs/assets/site.css`. Nav links are in-page anchors.
  - Basemap tiles are Esri's keyless gray canvas (`World_Light_Gray_Base` / `World_Dark_Gray_Base`, via the shared `basemapTiles()` near the top of the inline script). Don't switch back to CARTO's `basemaps.cartocdn.com`: it serves "API KEY REQUIRED" watermarked tiles without a key.
  - Uses CDN-hosted Leaflet + leaflet.heat. If you bump the Leaflet version, recompute the `integrity` SRI hashes on its `<link>`/`<script>` tags (`curl -s <url> | openssl dgst -sha256 -binary | openssl base64`) or the browser will silently refuse to load them.
- `CitiBike_2024.ipynb` — walkthrough of the 2024 analysis (cleaning stats, weather model, rebalancing, forecast evaluation). Recomputes everything except the forecast, which it reads from `docs/data/forecast.json` (retraining takes ~40 min). Execute with `jupyter nbconvert --to notebook --execute --inplace CitiBike_2024.ipynb` after the build scripts.
- `CitiBike_Analysis.ipynb` — an exploratory deep-dive into **January 2024 only** (EDA plus a member-vs-casual classifier). It is not the source of the site's numbers.
- `tests/` — pytest: unit tests for the pure logic in `scripts/`, leak tests for the forecast inputs, and consistency tests on the published data (totals agree across sections, `.js` wrappers match `.json`, bike lanes stay under 1 MB, prose facts match). `.github/workflows/checks.yml` runs pyflakes, `sync_facts.py --check` and pytest on every push; dev deps in `requirements-dev.txt`.

## Scripts (`scripts/`)

Every script takes a period: `YYYY` (full year, the default `2024`) or `YYYYMM` (one month).

- `pipeline.py` — the single source of truth: loading (`load_month`, zips cached in gitignored `.cache/`), cleaning (`clean`, logs rows removed per step and stores them in `df.attrs["cleaning"]`), a per-month cleaned parquet cache (`clean_month_path`, `.cache/clean/YYYYMM.parquet` plus `YYYYMM.stats.json`; `cleaning_stats(period)` sums them) and `load_clean_period(period, columns=...)`, NOAA weather (`load_weather_hourly` from LCD FM-15 reports, `load_weather_daily` from GHCN-Daily, Central Park station, cached in `.cache/`), and the notebook's classifier features (`engineer_features`, `FEATURES`). Never re-implement cleaning elsewhere. Each month is cleaned on its own and trips are assigned to the month they start in.
- `build_heatmap.py` — `docs/data/heatmap.{json,js}` (also carries the `riders` mix and `cleaning` totals the prose cites) and `docs/assets/heatmap.png` (the page's `og:image`).
- `build_geomap.py` — `stations.{json,js}` (per-station totals/hourly profile + `boro`), `bike_paths.{geojson,js}` (pulled live from [NYC Open Data](https://data.cityofnewyork.us/dataset/New-York-City-Bike-Routes/mzxg-pwib) with retries; the feed is not versioned and occasionally contains empty geometries, which are dropped; `compact_bike_routes()` merges segments by street/facility/borough and simplifies to ~4 m, taking the file from 6.4 MB to ~0.7 MB — the true segment count is kept in `summary.json` for the stat tile), and `summary.{json,js}`. Requires `shapely`.
- `build_seasonality.py` — `seasonality.{json,js}`: daily rides joined to NOAA daily weather plus hourly commute-window precipitation, binned dry-weekday rides by high temperature, and a log-linear model (day of week, holiday, temp + temp², mutually exclusive rain types off-peak / commute / heavy, snow, linear growth trend) with 95% CIs from a 14-day moving-block bootstrap. Snow and growth CIs are wide; the site doesn't headline them. The temperature terms are controls only: the quadratic can't capture the plateau-then-dip above ~30°C, so the site charts the binned averages.
- `build_rebalancing.py` — `rebalancing.{json,js}`: per-station average net flow (arrivals − departures) in the weekday AM (7–10) and PM (16–19) rush on non-holiday weekdays, top losers/gainers, by-borough totals, monthly "bikes to move" (sum of losing stations' average morning deficit, a lower bound that ignores dock capacity). Reads `stations.json` for boroughs, so run `build_geomap.py` first. Stations with < 1 rush trip per morning are excluded. Also reports the AM/PM correlation normalized by each station's rush traffic, since the raw one is inflated by station size.
- `build_forecast.py` — `forecast.{json,js}`: day-ahead station × hour forecasts of departures *and* arrivals with `HistGradientBoostingRegressor` (Poisson loss) on one hourly timeline covering 2024-01-01 to 2025-08-25 (hourly weather is only published to 25 Aug 2025; `WEATHER_END`). Trips are read one month at a time; counts and history features are matrices (stations × hours), and history inputs come from the pure function `history_features(y, nbr)`. `tests/test_forecast_features.py` proves no input for a day uses that day's counts and that the station profile ignores data after its cut. Add any new history input there, or the coverage test fails. Inputs, all known a day ahead: hour, weekday, holiday, observed weather (temperature, wind, rain this hour / past 3 hours / whole day), lag 24h, lag 168h, same-hour 7-day mean, same weekday-hour 4-week mean, yesterday's station total, 7-day mean daily total, yesterday's system demand vs. the prior week, yesterday's demand at the 5 nearest stations (`neighbor_lag_24`, no measurable gain in tuning), and the training-period station profile. Protocols: **headline** trains on everything before 2025-06-01 (early-stopped on April–May 2025) and tests June–August 2025; **benchmark** trains on 2024 only and is scored on the same months (training on the 2025 months improves error by under 1%); **yesterdays_weather** retrains with each weather input replaced by yesterday's value (a crude forecast; the site quotes the range, never the single best figure). `TUNING` picks settings on the headline validation months, trees are added in steps of 50 until a step improves validation MAE by < 0.05% (`MIN_GAIN`), cap 2,000. Training rows are capped at 15M and validation at 3M by a fixed random sample: the uncapped run was OOM-killed at 14 GB. Outputs: hourly MAE vs. four baselines (**same-hour 7-day mean is the strongest and the headline comparison**); `levels` = accuracy (1 − WMAPE) at station-hour, station-day, borough-hour, system-hour, system-day with a Poisson chance ceiling; weekday 7–10am net flow and precision@20; 80% bands = shortest range per bin of predicted level, rounded to the nearest trip, with the coverage level chosen separately for quiet, medium and busy hours so each covers 80% of the validation months (`calibrated_band`; the test months only receive the band; outward rounding over-covered by about five points); a rolling monthly backtest over June–August. **Don't add day-of-year or month inputs** (unseen values under a date split). `FORECAST_SMOKE_STATIONS=40` runs end to end in a few minutes and writes to `.cache/`. Full run ~1.5 hours, ~3 GB peak for the fitted matrices.

Regenerate via these scripts rather than hand-editing anything under `docs/data/`. Full run order: `build_heatmap.py`, `build_geomap.py`, `build_seasonality.py`, `build_rebalancing.py`, `build_forecast.py`, then `sync_facts.py --write` and the notebook. A full-year rebuild downloads ~7.5 GB of zips into `.cache/` the first time.

`assign_boroughs()` in `build_geomap.py` classifies stations by real borough polygon (point-in-polygon against NYC Open Data's [Borough Boundaries](https://data.cityofnewyork.us/City-Government/Borough-Boundaries/gthc-hcne)), not a lat/lng box. Stations outside all 5 boroughs (Jersey City/Hoboken stops that received a few cross-river trips) get `boro: "Other"`.

The ridership map's `fitBounds` padding (56px) must stay larger than the heat layer's `radius + blur` (14+16=30px), or edge-of-service stations (e.g. Riverdale, Bay Ridge) get clipped at the canvas boundary.

Prior to this, the repo contained `MTA_Analysis.ipynb` (NYC subway ridership; see git history on commits `cdfd951`, `2b3238c`, `0868b1a`), removed in favor of the Citi Bike analysis.

## Data sources

Nothing is committed; everything downloads at build time into gitignored `.cache/`:

- Trips: [Citi Bike System Data](https://citibikenyc.com/system-data), monthly zips at `https://s3.amazonaws.com/tripdata/YYYYMM-citibike-tripdata.zip`.
- Weather: NOAA NCEI access API (`www.ncei.noaa.gov`), Central Park station (LCD `72505394728`, GHCND `USW00094728`). Open-Meteo was tried first but rate-limits shared IPs.
- Bike lanes and borough boundaries: NYC Open Data (`data.cityofnewyork.us`).

## Notebook structure (`CitiBike_Analysis.ipynb`, January 2024)

1. **Load / Clean** — `pipeline.load_month()` and `pipeline.clean()` (duplicate `ride_id`s, out-of-month spillover, missing station/coordinates, non-positive durations, trips over 24h, in that order; `trip_minutes` must exist before the duration filters).
2. **EDA** — trip duration distribution, member vs. casual mix, ride timing by hour (normalized per group), average duration by rider type, day × hour heatmap, top 15 start stations.
3. **Predicting Rider Type** — `pipeline.engineer_features()` plus weather, day of week, and station/route casual rates encoded **out-of-fold** with `pipeline.target_encode_oof()` (computing them on all training rows leaked each trip's own label and dropped test AUC from 0.73 to 0.69), and route-relative duration. Time split: train Jan 1–24, test Jan 25–31. Unweighted `LogisticRegression` and `HistGradientBoostingClassifier`; the GBM reaches 89.6% accuracy vs. 89.1% for "always member", ROC-AUC 0.77, and 6.8x lift in the top 1% (75% casual). Evaluation leads with AUC, PR-AUC, a threshold table and lift, because accuracy can barely move above the 89% majority rate. The same model on all of 2024 lands at AUC ~0.76, so the ceiling is the data (casual commuters look like members), not volume.

Member vs. casual riders use a fixed color convention (`{"member": "#2a78d6", "casual": "#eb6834"}`).

Run with `pip install -r requirements.txt`, then top-to-bottom from the repo root (it imports `scripts/pipeline.py` via `sys.path`): `jupyter nbconvert --to notebook --execute --inplace CitiBike_Analysis.ipynb`.
